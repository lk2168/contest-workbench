# 同类项目调研（2026-10-03 在 GitHub 实搜）

> 调研方法：`gh search repos` 按模块分组查（电赛/备赛工作台/串口助手/PID 调参/ISP 烧录/题库），
> 再读最接近几个的 README 核实覆盖范围。**不是凭印象**。
> 项目的取舍原则（用户定的）：**先找现成的，别自己造；搜不到才自己做 —— 而"搜不到"本身就是机会**。

## 一句话结论

| 问题 | 答案 |
|---|---|
| 单个模块有同类吗？ | **有，而且很多**（串口助手、题库、ISP 烧录都成熟） |
| "AI 读赛题 → 出作战方案 → 硬件调参闭环 → 串口采数 → 烧录"这一整套串起来的有吗？ | ★ **没有** |
| 最接近的两个是什么？ | `mc3545dada/mspm0-skill`（★374，绑芯片的 Agent Skill）、`ZF3373/icpc-workbench`（★70，**别的赛道**的同形状工作台） |
| 我们最"独"的一块？ | ★ **阶跃指标 → 参数自动扫描 → 推荐参数**（GitHub 上几乎空白） |

## 按模块看

### ① 最接近：AI + 电赛（真的有人在做了）

**`mc3545dada/mspm0-skill` ★374 —— 面向电赛的 MSPM0 Agent Skill**

> 让 AI Agent 真正参与 MSPM0 的 SysConfig 配置、工程构建、烧录与调试。

它做的：改 `.syscfg` ✓、识别工程与工具链（CCS/Keil/CMake ✓）、自动构建与烧录
（DSLite/J-Link/OpenOCD ✓）、连真实硬件调试 ✓、**串口闭环验证/调参（Python 串口收发，可用于 PID 调试 ✓）**、
SDK 例程检索 ✓。已在真实板子上验证过（MSPM0G3507 + J-Link/DAPLink ✓）。

**和我们重叠的**：串口闭环调参 ✓、烧录 ✓
**和我们不同的**：
- 它是 **Agent Skill**（宿主是 Claude Code / Cursor / Codex 等 ✗），**不是独立应用** ✗
- **绑定 TI MSPM0 芯片** ✗（我们面向任意 STM32/串口设备 ✓）
- 烧录走的是**调试探针**（J-Link/DAPLink ✓），我们走**串口 BootLoader**（没有仿真器也能烧 ✓）
- ★ **完全不碰赛题分析**（没有赛题拆解 / 答疑检索 / 作战方案 ✗）

→ 它是"**把 AI 接进芯片开发工具链**"，我们是"**把 AI 接进备赛全流程**" ✓ 定位不同 ✓

### ② 同"形状"、不同赛道：`ZF3373/icpc-workbench` ★70

**ICPC 备赛工作台**：本地 Web 应用 → 多平台刷题同步 → 弱项分析 → AI 训练计划 → 题库 → 热力图 → 掌握度地图。

**形态上和我们最像**（本地 Web 应用 + 数据分析 + AI 生成计划 ✓），但赛道是**算法竞赛（刷题）** ✗，
完全不碰硬件 ✓。

★ **值得学的（产品化细节，我们现在缺）**：

| 它的做法 | 我们该不该学 |
|---|---|
| **自动恢复点**（每日首启/升级前/大批量导入前，SQLite `VACUUM INTO` 一致快照，按类型分级保留） | ★ 该学 —— 我们只有手动备份 |
| **同步/任务可观测性**（每次同步成败皆记：拉取数、失败分类、耗时，可导出诊断） | ★ 该学 —— 我们的"采集"没有这种可追溯 |
| **内置离线题库**（约 1.3 万题，首启自动入库） | 我们已有题库，但没做到"开箱即用" |
| **推荐冷却机制**（近期推过的进入冷却，不天天重复） | 可借鉴到"每日训练"类功能 |
| **多账号 / 本地安全边界**（默认只听 127.0.0.1） | 我们已经是本地优先 ✓ |

### ③ 题库（有 ★988 的强者）

- `CCBP/NUEDC_Topic` ★988 —— 1994–2026 历年赛题收集
- `zuoliangyu/NUEDC_TOPIC` ★111 —— 真题文档，更新到 2026
- 其他：`13060923171/Electronic-Design-Competition` ★156、`TANSUNS/NEDUC_lib` ★67（基础算法&模块）✓

→ 它们是**纯资料仓库** ✗（无分析、无答疑检索、不能出方案 ✓）。
★ 我们的题库功能**不必去比"谁的题全"** ✗，而要比"**能不能据此出可验收的方案**" ✓。

### ④ 串口助手（红海）

`SuperCom` ★1526、`llcom` ★1254、`Wu.CommTool` ★677、浏览器版 `SerialAssistant` ★909、
Linux 版 `sscom` ★191 ⋯⋯

→ 结论和上次调研一致：**不做"另一个串口助手"** ✗。我们做的是
"**采到的数据 → 自动算指标 → 自动扫参数**"这条闭环 ✓（前者是工具，后者是决策 ✓）。

### ⑤ ★ PID 调参上位机（GitHub 上几乎空白）

搜出来的顶尖结果：`Arduino-PID-AutoTune-Library` ★483（是个**库** ✗，不是上位机）、
`arduino-pid-autotuner` ★211（Arduino 端 ✗）、`pid-autotune` ★170（烧水壶仿真 ✗）、
中文的"PID 调参上位机"基本是 ★0–2 的个人项目 ✗。

→ ★★ **这是我们最"独"的一块** ✓：**阶跃指标（超调量/上升时间/±2%调节时间）+ 参数自动扫描 + 确定性推荐**，
在 GitHub 上没有成熟的同类 ✓（而且每一步都可手算复核 ✓）。

### ⑥ STM32 串口 ISP 烧录（成熟，直接用）

`stm32flash` ★252（**我们就是读它的源码才对上 Write 帧的** ✓）、`stm32duino/stm32flash` ★58、
`tomzbj/zboot` ★163（串口 BootLoader 实现）✓。

→ 这块**不该自己造** ✓（我们只是把它**集成进工作台**，做了"备份→擦除→写入→读回校验"的安全流程 ✓）。

## 我们的位置（诚实的自我评估）

**已有的差异化**：
1. ★ **赛题 → 可验收的作战方案**（含官方答疑检索、量化指标、"经验值需实测确认"标注）—— 没找到同类
2. ★ **阶跃指标 + 参数自动扫描 + 推荐**（确定性算法、可复核）—— 没找到同类
3. ★ **把 1 和 2 串在一个本地应用里**（不用在 5 个软件之间倒数据）—— 没找到同类
4. 串口 ISP 烧录的安全流程（先备份、读回校验、芯片 ID 不符就停手）—— 集成到位、不重复造

**我们的短板（要认）**：
1. **发现度**：同类项目 ★70–988，我们目前 ★1 —— 代码不是瓶颈，**被人看到**才是
2. **产品化细节**：缺自动备份/恢复点、缺任务可观测性、题库没做到开箱即用
3. 单一赛道（电赛控制类）天花板可见 —— 但也是能做深的地方

## 结论

> **单模块都有人做，整条链路没人串。**
> 我们要做的不是"更好的串口助手"或"更全的题库"，而是**唯一一个把赛题、调参、采数、烧录串起来的入口**。
> 而"阶跃指标 → 自动扫参数 → 推荐"这块在 GitHub 上确实空白 —— 按用户的原则，
> **"搜不到"本身就说明这是一个值得做的项目** ✓
